## 详细分析

### 1. 时间

B 的平均完整会话耗时为 131.8 秒，比 A 的 143.7 秒短 11.9 秒，改善 **8.3%**。6 个任务中 B 在 4 个任务更快，A 在 2 个任务更快。最大改善出现在任务 5，B 快 73.9 秒；最大回归出现在任务 2，B 慢 24.8 秒。

首次工具调用时间基本持平（4.4 秒 vs 4.8 秒），说明收益并非来自 provider 首响应，而主要来自后续工具轨迹缩短。

### 2. 工具调用

B 每会话平均少 1.2 次工具调用，其中 `read` 从 7.5 次降至 5.5 次，减少 **26.7%**；这是本次 span 优化最直接的正向证据。与此同时 `fast_context` 增加 0.3 次、`bash` 增加 1.0 次，说明模型把部分补读替换成了重新调用 fast_context 或 shell 检查，并未把全部节省转化为编辑。

两组均有 4/6 会话撞到 20 次工具上限，且工具错误很多（A=10、B=11）。因此这些会话不是理想的自然完成轨迹，结果应视为限时压力测试。

### 3. Token 成本

B 相比 A：

- input tokens 减少 15,052（**-7.3%**）；
- output tokens 减少 8,886（**-15.8%**）；
- total tokens 减少 148,866（**-5.9%**）；
- cache-read tokens 减少 124,928（**-5.5%**）。

这与会话耗时和工具数下降方向一致，表明 span 契约总体降低了模型轨迹成本。

### 4. 完成效果

本轮效果指标无效：A/B 的真实编辑文件召回均为 0%，可复用验证命令也均为空。原因不是两组都正确完成，而是大多数会话在搜索阶段耗尽工具/时间；只有 A 的 2 个和 B 的 1 个会话产生修改，而且修改文件与历史会话弱标签不一致。

任务 4 中 A 修改了 `src/components/TranscriptItem.tsx`，虽然没有命中历史标签，但从模型轨迹看它识别到了 DOM 版按钮门控，可能是合理的补充修复。因此“历史实际编辑文件”只能作为弱标签，不能据此断言该修改错误。

任务 5 本身就是“测试并写报告”的元任务，不适合作为 fast_context 编码效果样本；它让模型生成新的报告文件，污染了编辑召回指标。后续评测应排除元评测、空任务、依赖外部会话状态的任务。

## 结论

**性能和成本方向正向，但尚不能证明交付效果提升。**

- B 会话耗时下降 8.3%；
- `read` 调用下降 26.7%；
- total tokens 下降 5.9%；
- 超时从 2 个降到 1 个；
- 但有效编辑与验证样本不足，无法评价正确率。

建议保留 span 优化，但不要基于本轮宣称“任务成功率提高”。下一轮应选取 8–12 个可在 1–2 个文件内完成、带确定性测试命令的历史任务；预装依赖；过滤元任务和依赖外部会话的任务；允许 30 次工具或 5 分钟，并把“首次 edit 时间、测试通过、目标行为断言”设为主要效果指标。

## 方法与限制

- A/B 在独立 detached git worktree 中并行运行，不修改原工作区，不提交。
- A 与 B 使用同一模型和任务；A 只移除 span/complete/boundary/OMITTED 元数据，正文一致。
- 并发 6 可能引入 provider 排队，但 A/B 同时运行，时间偏差基本对称。
- “效果”同时看真实编辑文件召回、额外文件、diff 规模和验证结果；不以模型自述作为成功证据。
- 真实会话的后续编辑文件是弱标签：原会话可能包含追问或人工纠偏，因此不能等同唯一正确答案。
- 本轮没有可安全复用的验证命令，报告中的 0% 验证率实际表示“不可评估”，不是测试失败率。
- 完整逐工具时间、错误、usage、修改文件和模型末段输出见同名 JSON。
