# Polaris 第三轮收尾与 Command Code GLM A/B

## 采用的最终改动

A 为已提交的第二轮 `b0ef0cf`，B 为本轮最终代码。不重复计入前两轮收益。

- 符号缓存和请求视图中的 `FileEntry` 改用 `Arc` 共享。有文件更新时仍需复制外层 Map，但不再复制其他文件的符号/导入列表；生成请求视图也不深复制符号。仅开启已有 serde 的 `rc` 功能，无新依赖。双向序列化回归证明旧 bincode 磁盘格式保持兼容，无缓存版本升级。
- 文件清单和请求视图构建移出项目更新锁。**更新扫描仍串行**：曾实现锁外扫描+乐观合并，但相同冷请求重复解析使四路冷并发 284ms→313ms，已撤回整套发布合并实现。不能把未采用的锁外扫描当作最终优化。
- 完整实时搜索才允许缓存批量词根的空结果。rg 输出需满足 UTF-8、未到总/单文件行上限、无长行省略、无超时/输出字节超限。候选已裁剪的内存索引与后备路径不提供负命中证明，仍允许逐词补搜，避免错误丢掉调用方。
- 源码符号复用校验 size+mtime+行数，不再仅凭行数相同就复用旧符号；扫描读前/读后 stamp 不同则不发布混合状态。种子和依赖打包补上范围检查，降低查询期间编辑导致越界的风险。不同请求重新读取，不引入跨请求旧正文缓存。
- 经验库保存时，召回字段比较移到召回缓存锁外；只在最后短暂持锁删除确实失效且仍为同一快照的缓存。未改成异步保存，也未改整文件持久化策略，避免引入知识丢失或乱序落盘风险。

## 正式 A/B 方法

复用前两轮三项任务；语料仍固定为 `30126f7` 的 `src-tauri/src`、`src`、`scripts`。同一个 Rust release 二进制中的 A/B 模块，生产配置、独立缓存、交错顺序。语料 Git 为单个合成提交，不反映真实长历史仓库。

每任务 6 对，排除第0轮后，剩余5次取中位数。新增4路同时调用测试（同一任务；冷/热各3对），以及800文件×每文件20个符号的增量更新检查。

## 热检索结果

| 查询 | A / ms | B / ms | 变化 |
|---|---:|---:|---|
| 索引读取与发布 | 75.53 | 78.29 | 慢3.7% |
| 工具执行与预算治理 | 47.94 | 50.91 | 慢6.2% |
| 系统提示词与只读模式 | 35.18 | 28.13 | 快20.0% |

**15对热输出逐字一致，但不是全面提速。** 开发期复测曾基本持平，各任务小样本波动明显；不能把最好的一项外推为整体收益。源码新鲜度校验和rg完整性判定也存在额外成本。

独立冷进程3对输出均一致：A 163.26/187.80/194.32ms，B 146.32/171.58/193.62ms。不是冷OS文件缓存。

## 四路并发

每组4个相同查询同步起跑；冷/热各3对，报告组完成时间中位数：

| 场景 | A / ms | B / ms |
|---|---:|---:|
| 冷并发 | 262.59 | 275.96 |
| 热并发 | 132.20 | 134.05 |

6组A/B、每组4个输出均一致。**最终方案冷并发仍慢约5.1%，热并发慢约1.4%**；不宣称并发提速。保留更新串行是基于撤回的锁外扫描版本更慢，未来只有不同闭包争锁被实测为瓶颈时才值得引入按文件的扫描合并。当前更明确的收益是编辑后符号增量更新，而非同时冷启动同一任务。

## 符号增量更新

800个合成源码文件，每文件20个符号；先构建全量符号快照，再连续修改同一个文件8次，持有旧快照验证不可变性。排除第0次，剩余7次中位数：

| 操作 | A / ms | B / ms |
|---|---:|---:|
| 单文件修改后更新 | 3.0573 | 0.2501 |
| 同闭包无变更查询 | 0.4084 | 0.1279 |

受控增量更新计算减少约91.8%。该检查直接运行 `build_index`，包含metadata、文件读取和符号扫描，但不包含模型、完整Polaris打包或真实大仓库Git历史。原始数据、断言和生成过程留在同一可运行脚本中。

## Command Code GLM-5.3-Flash

实际请求和响应均为 `z-ai/glm-5.3-flash`。三任务×两次交叉顺序×A/B，总计12次正式调用。每次新会话、仅注入对应Polaris最终证据，不允许继续调工具；温度1、top_p 0.95、max_tokens 3000，无自动重试。

| 指标 | A | B |
|---|---:|---:|
| 完整返回 | 6/6 | 6/6 |
| 关键符号字面命中 | 10/10 | 10/10 |
| 辅助事实词命中 | 17/18 | 16/18 |
| 输入token总计 | 41,216 | 41,216 |
| 输出token总计 | 4,675 | 5,550 |
| 模型平均请求耗时 | 25.79s | 24.17s |

模型平均耗时约少6.3%，但两侧证据逐字一致、只有6次样本且输出token反而更多，不能归因于检索优化。辅助词命中有一项回落，字面命中不等于语义正确率。**没有完整Agent端到端提速或更高答案准确率的结论。**

## 验证与边界

52项上下文测试、4项经验库测试、2项常驻服务测试、8项Lyra工具测试通过，共66项；2项既有排序实验保持ignored。新增检查覆盖并发不同文件冷扫描、旧磁盘格式、完整/截断rg负命中证明、同等行数的编辑，以及前两轮既有增量/删除/超时检查。

本轮已对可确认的问题完成收尾，并撤回无收益的并发重构，不意味着所有理论优化都已实现：

- 项目更新锁保留，外层Map仍是O(n)浅复制；属于已实测权衡，而非遗漏的TODO。
- 内存索引仍有约2秒后台轮询窗口，固定请求快照不等于与同时发生的文件编辑完全同步。源码stamp校验降低旧符号风险，不提供文件系统事务快照。
- 内存候选裁剪/不完整搜索不能缓存负结果，必要补搜仍存在。
- 经验库首次召回仍可能等待保存持有的store锁，整文件保存策略未改变；本轮仅缩短热召回的cache锁等待，未做知识库规模性能测试。
- 所有API模型测试都不是完整Agent任务循环；测试未部署到当前 `/opt/nova/nova`，构建更新并重启后才生效。

## 复现

```bash
node bench/polaris-latency-ab.mjs --baseline b0ef0cf --corpus-ref 30126f7 \
  --cold-check --concurrency --symbol-update --model \
  --out bench/polaris-round3-ab.report.json
```

默认不调用模型，只有 `--model` 消耗Command Code额度。原始报告包含最终源码SHA-256、逐次延迟、文件清单、证据哈希、冷查询正文、并发和符号更新数据、模型回答与用量。撤回的锁外扫描版本数据仅用于上述决策说明，未混入正式表格。
