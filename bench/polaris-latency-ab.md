# Polaris 热路径优化与 Command Code GLM A/B

## 结果

采用两项生产优化：

- 符号索引无变更时借用 `Cow` 快照，避免锁内复制全仓符号表；反向图由同一 `Arc<DiskCache>` 共享，不再单独深拷贝。实际变更仍复制并原子发布，已有读者不受影响。
- 将现有源码缓存扩展到整个请求，种子、调用图、候选、依赖、回填复用源码；`Source` 的拆行和符号列表使用 `Arc`，打包克隆不再复制全文。不同请求不共享此正文缓存。

未改变搜索预算、排序、候选上限和 Git 历史策略。暂未采用“缓存补搜空结果”：搜索返回值不能区分确实零命中与超时/截断，贸然缓存可能漏掉必要补搜。

## 正式工具 A/B

A 是 `30126f7` 的原生模块，B 是本次修改。两侧以同一个 Rust release 二进制编译运行，启用生产搜索索引/deadline（不是 cfg(test) 路径），使用独立数据缓存。检索语料相同：从基线提交导出 `src-tauri/src`、`src`、`scripts`，避免新评测脚本或答案进入检索。语料创建一个独立 Git 提交，不包含原仓库共改历史。

3 类查询，每类 6 对，交错 A/B 顺序。第 0 轮只作首次观测，余下 5 轮取中位数：

| 查询 | A / ms | B / ms | 降幅 | 热查询正文 |
|---|---:|---:|---:|---|
| 索引读取与发布 | 125.2 | 86.6 | 30.9% | 5/5 对逐字一致 |
| 工具执行与预算治理 | 62.4 | 55.7 | 10.8% | 5/5 对逐字一致 |
| 系统提示词与只读模式 | 35.8 | 28.9 | 19.3% | 5/5 对逐字一致 |

全部 15 对热查询输出哈希相同，输出均未超过 32KB。

**冷启动例外**：正式实验第 0 轮索引查询，两侧主目标文件均返回，但辅助文件不同（A 包含 experience/lib，B 包含 cursor-context-reasonix/super）；此后热查询一致。补跑 3 对独立空缓存进程的冷查询，输出全部一致。现有后台全文索引异步就绪会使冷查询在 rg 与内存检索之间切换，这是可能原因，但本次未做分支追踪证明，不能宣称冷启动完全等价或该问题已修复。

## Command Code GLM-5.3-Flash

实际端点：Command Code 配置的 `/chat/completions`，请求和响应模型均为 `z-ai/glm-5.3-flash`。凭据只从本机已有配置读取，未写入脚本或结果。

正式实验 3 任务 × 2 次交叉顺序 × A/B = **12 次模型调用**。每次创建新消息上下文，并注入该侧最后一轮 Polaris 工具结果；模型不能继续调工具。温度 1、top_p 0.95、输出上限 3000 token，无自动重试。

| 指标 | A | B |
|---|---:|---:|
| 完整返回 | 6/6 | 6/6 |
| 关键符号字面命中 | 10/10 | 10/10 |
| 辅助事实词命中 | 16/18 | 16/18 |
| 输入 token 合计 | 41,216 | 41,216 |
| 输出 token 合计 | 4,547 | 6,578 |
| 模型请求平均耗时 | 24.60s | 29.21s |

模型证据输入相同，两侧回答均覆盖主要流程；B 有一次 46.7s 的较长回答。**没有测得模型端提速，也没有节省输入 token**。字面命中只是冒烟检查，不等于语义准确率；回答仍有遗漏/不严谨表述，例如将证据中的两套实现直接视为两条现役链路、依据签名推断部分运行行为，不能报告为“答案完全正确”。

这是工具延迟 A/B 加受控模型证据检查，**不是完整 Agent 多轮任务基准**；不包含模型自主选词、额外 read、Lyra 知识召回或桌面/UI耗时。首次观测也不是冷 OS 文件缓存。因而只可确认这批样本的热检索提速，不可外推为所有大仓库、并发场景或整轮对话的同比提升。
